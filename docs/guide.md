# Как мы строим Mira — понятное руководство

Этот файл — не план по датам (за это отвечает `roadmap.md`), а объяснение
**зачем и как** устроен каждый шаг, чтобы ты понимал систему сам, а не просто
набирал код. Читай его перед началом этапа.

---

## 0. Модель, из которой всё растёт

Процессор — это очень тупой, но очень быстрый исполнитель. Всё, что он делает,
укладывается в цикл из трёх шагов:

1. **Fetch** — посмотреть на адрес в `pc` и взять оттуда 4 байта.
2. **Decode** — понять по этим байтам, *что* за операция.
3. **Execute** — изменить регистры/память и передвинуть `pc`.

Всё остальное — это детали: какие бывают операции, где лежат данные, что делать
при ошибке. Поэтому наш эмулятор — это буквально `loop { step() }`, где `step()`
делает эти три шага.

Три вещи, которые надо держать в голове:

| Понятие   | Что это                                                        |
|-----------|----------------------------------------------------------------|
| Регистры  | 16 «ячеек» по 64 бита прямо внутри CPU. Быстрые, но их мало.    |
| Память    | Большой массив байт (`Vec<u8>`). Медленнее, но вмещает всё.      |
| `pc`      | Адрес *следующей* инструкции. Меняется почти каждой командой.   |

---

## 1. Кто за что отвечает

```
mira-cpu   — «железо»: регистры, память, выполнение инструкций. Никакого ввода-вывода.
mira-asm   — переводчик текста (.s) в байты, которые понимает mira-cpu.
mira-emu   — «компьютер»: загружает программу, подключает UART/клавиатуру, крутит CPU.
docs/      — договорённости. Если код спорит с docs — прав docs, код надо чинить.
```

Важное правило: `mira-cpu` ничего не печатает и не знает про терминал. Он только
меняет своё состояние. За терминал отвечает `mira-emu`. Это позволяет тестировать
CPU в чистом виде.

## 2. Этапы

Ниже — что делаем и **какое понятие осваиваем** на каждом этапе. Отмечай
пройденное.

### ✅ Этап 0. Каркас
- **Цель:** `cargo build` работает.
- **Осваиваешь:** Cargo workspace, зачем делить проект на крейты.
- **Готово:** сборка проходит.

### ✅ Этап 0.5. Спецификация ISA
- **Цель:** до кода договориться, как выглядят инструкции.
- **Осваиваешь:** что такое кодировка (encoding), поля инструкции, форматы
  R/I/S/B/J, соглашение о вызовах (ABI), карта памяти.
- **Почему так рано:** без общей кодировки CPU и ассемблер не поймут друг друга.
  Спека — это «договор», а не документация «для галочки».
- **Готово:** `docs/isa.md` + `docs/memory-map.md` описывают всё, что нужно
  для первой инструкции.

### ✅ Этап 1. Простейший CPU
- **Цель:** выполнять 5 инструкций: `ADDI`, `ADD`, `SUB`, `JAL`, `EBREAK`.
- **Осваиваешь:** структура `Cpu`, чтение little-endian, знаковое расширение
  (`sext`), декодирование по битовым маскам, `Trap` (ошибки), `r0 = 0`.
- **Ключевая мысль:** `step()` возвращает не «ничего», а результат —
  `Continue` или `Halt`, либо `Trap`. Это позволяет эмулятору и тестам
  одинаково реагировать на остановку и на ошибку.
- **Готово:** `cargo test -p mira-cpu` — 16 тестов зелёные.

### ✅ Этап 1b. Ассемблер
- **Цель:** писать программы текстом, а не массивами байт.
- **Осваиваешь:** две фазы сборки (сначала метки и адреса, потом кодирование),
  метки (labels), директивы `.org`/`.word`/`.byte`/`.asciz`, псевдоинструкции
  (`mov`, `li`, `j`, `call`, `nop`), относительные смещения переходов.
- **Почему «две фазы»:** `j end` стоит *до* метки `end`. Адрес `end` станет
  известен только когда пройдём весь файл. Поэтому первый проход считает только
  адреса, второй — подставляет числа.
- **Готово:** `cargo test -p mira-asm` зелёные; программы из текста грузятся в CPU.

### ⬜ Этап 2. Эмулятор и первый вывод
- **Цель:** `cargo run -p mira-emu` запускает программу и печатает что-то в терминал.
- **Осваиваешь:** MMIO (Memory-Mapped I/O) — «магические» адреса, при записи
  в которые происходит не память, а действие (вывод символа). Останов по
  `EBREAK`/выходу `pc` за программу. Дамп регистров.
- **Почему MMIO:** это самый простой способ дать программе поговорить с миром,
  не усложняя сам CPU. CPU как будто пишет в память — а эмулятор перехватывает.
- **Готово:** тестовая программа выводит строку.

### ⬜ Этап 3. Расширение ISA
- **Цель:** инструкции для настоящего кода.
- **Осваиваешь:**
  - Группа 1: `LD/SD/LB/SB` (данные), `BEQ/BNE/BLT/BGE` (условия), `JAL/JALR`
    (вызовы и возвраты) — вместе это уже позволяет циклы и функции.
  - Группа 2: `AND/OR/XOR`, сдвиги, сравнения — логика и битовые операции.
  - Группа 3: `ECALL` (системный вызов), `LUI/AUIPC` (большие константы).
- **Почему группами:** после каждой группы — тесты. Иначе к концу этапа
  непонятно, какая именно инструкция сломалась.
- **Ключевая мысль:** `JALR` + соглашение об `ra`/`sp` = функции. Это момент,
  когда CPU из калькулятора превращается в вычислитель.
- **Готово:** программа считает и печатает результат, есть функции и циклы.

### ⬜ Этап 4. «Hello from Lyra»
- **Цель:** появляется ядро.
- **Осваиваешь:** загрузка образа в память, инициализация стека (`sp`),
  стартовая точка. Ядро — пока просто код, вшитый в эмулятор (`include_bytes!`).
- **Почему не отдельный бинарник:** собрать бинарник под наш самодельный ISA
  нельзя обычным `cargo build` — нужен кросс-тулчейн и линкер. Это отдельный
  большой проект, поэтому Вариант A (ядро внутри эмулятора).
- **Готово:** при запуске видно `LyraOS-2 booting...` и `Hello from Lyra`.

### ⬜ Этап 5. Syscalls и пользовательский код
- **Цель:** программы обращаются к системе через `ecall`.
- **Осваиваешь:** договор о системных вызовах: номер вызова в регистре, аргументы
  в `a0..a3`, результат в `a0`. Syscalls `write`, `exit`, позже `read`.
  Примитивный shell (`help`, `echo`, `exit`).
- **Почему через `ecall`, а не напрямую:** пользовательский код не должен сам
  трогать UART. Он просит систему — так возникает граница «приложение ↔ ОС».
- **Готово:** в консоли `echo hello` даёт ответ.

### ⬜ Этап 6. Обучающий софт
- **Цель:** `mira-lessons` — уроки (регистры, стек, вызов функции, syscall).
- **Осваиваешь:** как учить других тому, что построил сам.

## 3. Как вносить любое изменение (порядок — важен)

Когда добавляешь новую инструкцию, всегда иди в этом порядке:

1. **`docs/isa.md`** — описать кодировку и семантику. Если этого не сделать,
   через месяц ты сам не вспомнишь, что означает `funct3 = 010`.
2. **`mira-cpu/src/isa.rs`** — константы и функция-энкодер (для тестов и asm).
3. **`mira-cpu/src/cpu.rs`** — декодировать и выполнить в `step()`.
4. **`mira-asm`** — добавить мнемонику, чтобы писать её текстом.
5. **Тест** в `mira-cpu` (семантика) и в `mira-asm` (сборка).
6. **`docs/guide.md`/`roadmap.md`** — отметить, что этап продвинулся.

Так изменение всегда согласовано на всех уровнях.

## 4. Глоссарий

| Термин | Простыми словами |
|--------|------------------|
| ISA | Набор инструкций, которые понимает CPU. Наш — CuckooCPU-2. |
| Кодировка | Как число-инструкция раскладывается по битам (opcode, rd, imm…). |
| Декодер | Код, который режет 32 бита на поля и решает, что делать. |
| `pc` | Program Counter — адрес текущей/следующей инструкции. |
| Little-endian | Младший байт числа лежит первым в памяти. |
| ABI | Договор, какой регистр для чего (аргументы, возврат, стек). |
| Стек | Область памяти для вызовов функций; растёт вниз, `sp` = вершина. |
| Trap | Ошибка выполнения: нелегальная инструкция, битый адрес и т.п. |
| MMIO | Адреса, которые на самом деле управляют устройствами, а не памятью. |
| Syscall | Просьба программы к ОС через `ecall`. |
| Assembler | Перевод текста в машинные байты. |
| Метка (label) | Имя для адреса, чтобы прыгать `j loop`, а не `j 0x104`. |
